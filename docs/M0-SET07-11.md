## Shared backend interfaces

Domain services resolve identity through current_identity, obtain a distinct user-scoped database client, and call narrowly reviewed RPCs. User tokens remain excluded from response serialization and repr. Memberships are resolved from the verified Auth subject and active database membership, never browser role/tenant headers. Service keys are rejected as public-key configuration. No generic SQL/privileged worker HTTP endpoint exists.

AuditRecord/OutboxEvent carry actor, timestamp and correlation ID. UnitOfWork defines the single transaction boundary for later direct-connection repositories. Existing SQL RPCs already atomically write operational data/audit/outbox. The protocol is not a new concrete PostgREST multi-write transaction or a worker implementation. Do not claim that writing three independent HTTP calls is atomic. Future adapters must implement this boundary or use a reviewed atomic RPC.

Supabase live Auth verification is implemented but tested here with provider fakes, not an account in a hosted project. DB-01 remains unchecked until native integration checks pass. Operational shipment/receipt/analysis/approval APIs are still explicitly planned in OpenAPI; /health and /api/me are labeled implemented. Running create_app without configured Auth never trusts a submitted token.

## Local verification

Install npm dependencies and the backend development requirements in the root .venv. The npm Python runner selects that interpreter automatically, or uses PYTHON/an installed Python in CI. Pydantic is pinned so schema output can be compared exactly.

Run `npm run typecheck`, `npm run build`, `npm test`, `npm run test:frontend`, `npm run test:backend`, `npm run test:contracts`, `npm run check:migrations`, `npm run test:database`, and `npm run test:browser`. Browser tests use Playwright Chromium by default; for installed Chrome on Windows set `$env:PLAYWRIGHT_CHANNEL = 'chrome'` first.

Local checks validate 10 frontend transport scenarios, 11 backend identity/security/policy tests, 11 contract fixtures, generated DTO/OpenAPI drift, migration conventions, the native smoke SQL on the isolated engine and 35 database integration scenarios. Browser checks compare existing demo content/screenshots and the shared-client preview on desktop/mobile. Exact commands/results are recorded in the checklist when verification finishes.

The new CI YAML has not run on GitHub because this work has not been pushed. PostgreSQL 17 service execution awaits that runner; local SQL tests use PGlite PostgreSQL 18 with test-only Auth/Storage stand-ins. Native Supabase Auth/Storage, Realtime, true concurrency and a hosted pilot remain later acceptance checks. Branch protection must be configured by a repository administrator; creating a workflow does not enforce branch rules.
